## Why it's organized this way

**Route groups `(auth)` and `(app)`.** Parentheses keep a folder out of the URL, so `(app)/leads` is served at `/leads`. Each group gets its own layout: the auth pages get a centered card, the app pages get the sidebar shell. Logged-in and public pages never share chrome.

**`app/` is routing only.** Pages are thin Server Components. They call `features/<module>/queries.ts` for data and render `features/<module>/components`. Business logic stays out of `app/` so it can be reused and tested.

**`features/<module>/` files:**

| File | Runs on | Purpose |
|------|---------|---------|
| `queries.ts` | Server | Reads data through the server Supabase client. Called from Server Components. |
| `actions.ts` | Server (`'use server'`) | Handles mutations: validates with `schemas.ts`, writes, then calls `revalidatePath`. |
| `schemas.ts` | Both | Zod schemas, shared by client forms and Server Actions. |
| `types.ts` | Both | Domain types derived from `database.types.ts`. |
| `components/` | Mostly client | Forms, tables and cards specific to that module. |

**Server Actions instead of API routes.** Internal reads and writes don't need REST endpoints. `app/api/` is reserved for callers outside the app:
- webhooks from lead sources, e-sign and MLS services
- cron jobs that run automations
- the ICS feed that calendar apps subscribe to

**Next.js 15 specifics.** In dynamic routes, `params` is a `Promise`, so every `[id]` page does `const { id } = await params`. A segment's `loading.tsx` and `error.tsx` give it streaming and error boundaries automatically.

## Database (`supabase/migrations/`)

| Migration | Contents |
|-----------|----------|
| `…0001_auth_organizations` | `organizations`, `profiles` (the app's users), `memberships`, signup trigger, RLS helpers |
| `…0002_core_crm_schema` | `contacts`, `leads`, `buyers`, `sellers`, `properties`, `transactions`, `tasks`, `notes`, `files`, `appointments` |
| `…0003_storage_crm_files` | Private `crm-files` bucket. Objects live at `<org_id>/…` and are scoped by RLS. |

```
organizations ─┬─ memberships ── profiles (auth.users)
               └─ contacts ─┬─ leads ─┐
                            ├─ buyers ┼─ transactions ── properties ── sellers
                            └─ sellers┘
  tasks · notes · files · appointments → link to any of contact/lead/buyer/seller/property/transaction
```

- **Composite foreign keys** like `(organization_id, contact_id)` mean the database refuses any cross-organization link.
- **User assignments** (`assigned_to`, `agent_id`…) reference `memberships`, so you can only assign people in your own organization.
- **Deleting records:**
  - Notes and files are deleted along with their parent record.
  - Tasks and appointments are kept, and their link to the deleted record is cleared.
  - A property can't be hard-deleted while a transaction references it. Main records have `deleted_at` for soft delete instead.

**Buyers and sellers are both contacts.** They have separate routes and features for their workflows: buyer criteria and showings for buyers, listing agreements for sellers. In the database, both will be role-specific profiles that reference `contacts`, so one person can be a buyer and a seller at the same time.
